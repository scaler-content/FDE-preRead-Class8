The Second Problem in the Same Case

Last class, you connected Meridian’s orders, support cases, issues, and human reviews to investigate a customer’s delivery question. The records did not all tell the same story, so the team needed evidence before deciding what to tell the customer.

Now a second message arrives on that same support case: an item is missing from the order. Meridian wants to keep the existing case and record this as a separate problem. When the team tries to add it, the current database design gets in the way.

What should change? And how would you know that the change has preserved everything already recorded about the first issue?

There is another surprise. After the change, a report shows more time spent on reviews, even though no additional review work took place. The SQL runs without an error. So where did the new total come from?

This is the kind of request an FDE encounters when a customer’s needs grow: a small change to the workflow can affect the meaning of existing data and reports. In Class 8, you will investigate the problem in MySQL Workbench, make predictions before running queries, and decide what evidence Meridian would need before trusting the result.

Before class

You do not need to write SQL in advance. Recall what one row represents in the support_cases, issue_records, and human_reviews tables. Come ready to answer the three questions below.

Questions to consider

  2. What would convince you that the original issue survived a design change?
  3. Why might a report total change when no new review took place?
